# Remediation storyboard — one real cause

Nov 6, 2026 · Companion to *Remediation Hub — End-to-End Lifecycle and Compliance Model*. One cause, followed from detection to done, to test whether the process convinces before any more UI is built.

> Context document supplied by the product owner, kept with the v4 build pack for reference. See also `lifecycle-and-compliance-model.md` in this folder.

## 0. The pattern this storyboard instantiates

The process must hold for any data product, source system, site or rule, or it is a one-off. So it is defined in three layers: a core that is identical everywhere, a registry filled once per data product, and four decisions a trustee takes per finding. Adding a data product means filling the registry. Nothing in the screens or the state machine changes.

**Core, fixed for everyone**

| Concept | Definition |
| --- | --- |
| Finding | Failures grouped by dataset × symptom × site. The unit of work in every domain. |
| Symptom | What the engine can see, derived from check type. Closed list: missing · invalid value · out of range · wrong format · orphaned reference · out of sequence · inconsistent · duplicated · not generated by the load. |
| Population segments | Every dataset's records fall into four: **in flight** (correctable as normal work) · **recently closed** (correctable only under control) · **historical** (immutable) · **new since detection**. Computed from two fields every dataset must declare: a lifecycle status and a creation timestamp. |
| Root cause vocabulary | Controlled, system-agnostic: optional in source template · no validation at entry · interface or mapping drops value · legacy migration · training or practice · master record not created · process sequence · duplicate entry · load logic · check too broad. Chosen by investigation, never by the engine. |
| Levers | Always five: stop the bleed · backfill under control · accept · fix the load · fix or re-scope the check. An action = lever + owner role + channel + reference + effective date. |
| Approvals | Who must concur on scope, impact, actions and acceptance is a function of tier × field criticality × segment, not of the product. |
| Verification | Two signals: new records clean since the effective date for N checks · in-scope backlog at zero or accepted. |
| Priority | Impact score = tier × field criticality × in-flight and recent records affected × age against target. Historical volume is deliberately excluded. |

**Registry, configured once per data product**

- Tables: plain name, source system, site field, record key field, lifecycle status field with its closed values, creation timestamp field.
- Fields: display name, criticality (CDE or not).
- Tier from the data-product register; trustee role.
- Channels per source system × lever: change-request system, ticketing, CAPA route, owner role per site.

**Per finding, the trustee's four decisions**

Scope → Investigate → Action plan → Verify. Every finding, every domain, the same four. The rest of this document walks one finding through them; section 5 walks three unrelated ones side by side to show the shape does not change.

> Note (v3/v4): the prototype now compresses these four decisions into one confirmation of a system-drafted proposal, with the same content (scope, root cause, action plan, Quality flag). See section 5 of the lifecycle model.

**What scaling stresses.** Volume: thousands of checks must compress into a short, impact-ranked queue. Heterogeneity: only channel and owner vary by system; the trustee sees LIMS and SAP findings as the same thing. Sites: a finding is per site from the start; cross-site is a roll-up. Rules load: the *check too broad* lever will fire often early; it must feed scoping metadata back into the catalogue rather than a hundred disputes.

## 1. The cause, as the engine reports it

**Batch genealogy links** (MES, Manufacturing, GxP critical). Five fields empty: Material quantity, Manufacturing end date, Material ID, Lot internal ID, Lot ID. **240,097 records failing.** First seen 21 September. Decision table says: *Not entered in the source system → Source-system owner → Fix at source.*

The first instinct, and what the current prototype encourages, is to send those 240,097 records to the MES owner for correction. That request would never be actioned. Closed batch records in a validated MES are not opened for retyping; even where a correction is technically possible it is a change-controlled activity per record. The cause would sit in *Waiting on fixer* until everyone stopped looking at it.

The number that matters is not 240,097. Split by when the batch was created, the same cause reads:

| Population | Records | What can actually happen |
| --- | --- | --- |
| Batches closed before 2024 | 237,900 | Nothing will be retyped. Decide whether to accept the history. |
| Batches closed in the last 12 months | 2,020 | Possibly correctable under a controlled backfill; depends on site procedure. |
| Batches open today | 177 | Correctable now by the people running them, in MES, as part of normal work. |
| New batches since detection | still arriving | The only part that gets worse every week. Stop it first. |

That split is the remediation. Everything the trustee does afterwards follows from it, and the Hub shows none of it today.

## 2. Day 1 to day 30

**Day 1 — Scope (trustee, 20 minutes).** The Manufacturing trustee opens the cause and sees the split above. She confirms the five checks are right (a batch record without a material quantity is a real problem) and sets the scope: *open batches and batches closed in the last 12 months are in scope; history before 2024 goes to an acceptance decision.* That is one recorded decision with a reason; because the data is GxP critical the site QA approver concurs the same day. The Hub now shows 2,197 records in scope and 237,900 parked, and stops presenting 240,097 as the problem.

**Day 1 — Impact (trustee and QA, same conversation).** Genealogy links are what a recall relies on. Before the history can be parked, QA asks whether missing material and lot IDs on closed batches mean traceability cannot be demonstrated. For 237,900 records the answer is "possibly", so a deviation is raised in TrackWise (DEV-26-3310) and the history decision becomes QA's, run through that deviation. The finding records the deviation reference. Had the fields been non-critical, impact would have been "none" and the history would have gone straight to a trustee acceptance.

**Day 2 to 5 — Investigate (trustee with the MES business owner at the site).** Why are five fields empty on a quarter of batches? Thirty minutes with the MES business owner and one look at the records by site answers it: at one site the recipe step that captures these values is optional in the MES template, and the interface drops the quantity when the unit is blank. Two root causes, both findable, neither visible from the rule. The same template runs at two other sites; a one-line check shows one of them has the same gap at a lower rate, so the finding is extended to that site and the third is cleared. The trustee records them from a controlled list: *Field optional in source template* and *Interface mapping drops value*, with a note. The decision table's label, *Not entered in the source system*, was the symptom that pointed her here; it was never the cause.

**Day 5 — Decide the actions.** One cause, four actions, each with its own owner and channel:

| Action | Lever | Owner | Channel | Reference |
| --- | --- | --- | --- | --- |
| Make the five fields mandatory in the MES template at the site | Stop the bleed | MES business owner | MES change request | CR-2026-0481 |
| Fix the interface to keep quantity when unit is blank | Stop the bleed | Data engineering | DE ticket | BICN-1920 |
| Correct the 177 open batches in MES as part of batch review | Backfill, permitted | Production supervisors via MES owner | Site procedure, no ticket | note on cause |
| Accept 237,900 historical records, review in 12 months | Accept | Trustee + QA approver | Hub acceptance, two signatures | ACC-0117 |

The 2,020 closed-but-recent records are left in scope and not actioned yet: whether a controlled backfill is permitted is a QA question raised on the cause, and the answer decides whether they join the backfill or the acceptance. Raising the question is itself the recorded step.

**Day 6 to 30 — Execute, outside the Hub.** The change request goes through MES change control; realistically that is three to six months, not weeks, so an interim control is recorded on day 6: supervisors check the five fields at batch review until the template change is live. The DE ticket is scheduled. Supervisors correct open batches as they review them. The Hub does none of this work; it holds the four references and reads their status weekly, and it keeps running the checks.

**Day 30 — Verify.** The interim control has been in place since day 6; since then no new batch has failed any of the five checks: the bleed has stopped, by procedure for now and by the template once the change request is live (verification is re-run against that effective date when it lands). Open-batch failures went from 177 to 9, the nine being batches opened before the change. The interface fix is live and the quantity count among new records is zero. QA answered that recent closed batches may not be backfilled; the 2,020 move into the acceptance, which is re-signed with the new count.

**Day 45.** Three consecutive weekly checks with no new failures and zero in-scope records. The cause closes. The history sits in the acceptance register with a review date in November 2027.

## 3. What done means

Two signals, both from the engine, both required:

1. **The bleed has stopped.** No record created after the corrective action's effective date fails the checks, for three consecutive weekly checks. This is the signal that the process was fixed, and it is the one leadership should care about most.
2. **The in-scope backlog is zero.** Every in-scope record either no longer fails or has been moved into a signed acceptance. Historical records parked at scoping do not block closure; they are governed by the acceptance's review date.

A cause with signal 1 and not signal 2 is *Fixed going forward, backlog open*. A cause with signal 2 and not signal 1 is not fixed at all, whatever the backlog says. Today's model has one signal, zero failing ever, which this cause would never reach.

## 4. What this changes in the Hub

The UI gets smaller, not bigger. The trustee's work is four recorded decisions, and the screen should be built around them.

| Added | Removed or demoted |
| --- | --- |
| **Population split** on every cause: history · recent closed · open · new since detection, with counts. Needs the record's creation date or batch status in the ledger. | The single failing count as the headline number. It stays as a total, below the split. |
| **Scope** as the first decision: which populations are in scope, with reason. | *Dispute the rule* as a top-level action. Most disputes are scope; the true rule challenges remain, one level down. |
| **Root cause found**, from a controlled list (field optional in template · no validation · interface mapping · legacy migration · training · master record not created · business exception · other), with a note. The engine's label is renamed **symptom**. | *Probable cause* language that implies the decision table diagnosed anything. |
| **Action plan**: one or more actions, each with lever (stop the bleed · backfill · accept · fix load · fix check), owner role, channel, external reference, effective date, status. | *Send for correction* as the one primary button. Sending is one action type among five. |
| **Two verification signals** shown separately: new records clean since effective date · in-scope backlog. | *Zero failing ever* as the only closure rule. |
| **Priority by impact**: open and recent records affected first, volume second. | Sorting by total record count. |
| **Fixer view** becomes a status read-back from the channel (CR, DE ticket, acceptance), not a queue of records to correct. | The fixer *Mark as done* on records. Done is the effective date of the action. |

What the data layer needs, over and above the current ledger ask: a lifecycle status field and a creation timestamp per table, declared in the registry so the four segments can be computed for every dataset, a site field per table, field criticality per column, an *effective date* per corrective action, and the engine evaluating new-since-date separately from the backlog.

One decision for the workshop that this storyboard exposes: whether the quality score is computed on the in-scope population with accepted history shown beside it as its own number, or stays whole-population and leadership learns to read two figures. Left undecided, Batch Genealogy sits at 88% with an empty cause list and nobody can say why.

If this storyboard reads as how it would really go, the next step is to rebuild the cause screen around sections 1 to 3 and strip the rest, then re-run the Batch genealogy walkthrough with one trustee before the workshop.

## 5. Three unrelated findings, the same four decisions

If the pattern is right, three findings that share nothing (different domain, source system, symptom, lever) walk through identical steps with identical vocabulary. If any column needs a concept the others don't, the core is incomplete.

|  | Batch genealogy links (MES, Manufacturing) | Material master by plant (SAP ERP, Supply Chain) | Change control records (TrackWise, Quality) |
| --- | --- | --- | --- |
| **Symptom** (engine) | Missing: five fields empty | Orphaned reference: plant code not in plant master | Out of sequence: approval date before creation date |
| **Segments** | 177 in flight · 2,020 recent · 237,900 historical · new arriving | 14 active materials · 0 recent · 1,310 inactive · new arriving at 2/week | 3 open change controls · 41 closed this year · 6,200 historical · none new since July |
| **Scope** (trustee; QA concurs on GxP critical) | In flight + recent in scope; history to impact assessment | Active materials in scope; inactive to acceptance | Open + recent in scope; history checked for impact then accepted |
| **Impact** | Traceability gap on closed batches → deviation raised, QA owns history decision | Planning runs skip orphaned materials → business impact, not GxP | Audit-trail inconsistency on closed records → QA review of a sample, no deviation |
| **Root cause** (investigation) | Optional in source template (site A) · interface drops value | Master record not created (plant created in SAP, not yet in plant master feed) | Legacy migration (dates swapped in the 2021 TrackWise upgrade) |
| **Actions** (lever · owner · channel) | Stop the bleed · MES owner · CR · Fix the load · DE · ticket · Backfill in flight · supervisors · site procedure · Accept history · trustee + QA · acceptance | Stop the bleed · MDM · plant master process fix · Backfill · MDM · create 14 plant records | Fix or re-scope the check · Rules team · scope check to records created after upgrade · Accept history · trustee + QA |
| **Interim control** | Manual check at batch review until CR live | None needed; backfill is same week | None; no new records affected |
| **Verify** | New clean since CR live · in-scope backlog 0 | New clean since process fix · 14 resolved | No new failures · in-scope 0 after re-scope |
| **Done** | Day 45, with history in the acceptance register | Day 10 | Day 7, with a catalogue change recorded against the check |

Three different timelines, three different levers, one shape. The only things that changed between columns are registry values (system, channel, owner role, lifecycle field) and the trustee's judgement.
